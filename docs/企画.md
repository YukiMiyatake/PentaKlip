# PentaKlip 企画書

## 1. 概要

**PentaKlip** は、League of Legends（LoL）のリプレイからキル・集団戦などの名シーンを自動検出し、ハイライト動画として切り出して保存するツールである。

リプレイを「見て探す」手間を減らし、自分の試合や観戦リプレイから短時間で見応えのあるクリップを得られることを目指す。

---

## 2. 目的

| 項目 | 内容 |
|------|------|
| 主目的 | LoLリプレイからハイライトシーンを自動検出し、動画として保存する |
| 対象ユーザー | 自分の試合を振り返りたいプレイヤー、クリップを量産したい配信者・コンテンツ作成者 |
| 成果物 | シーン単位のハイライト動画（および検出結果メタデータ） |

---

## 3. 解決したい課題

1. **シーン探しが面倒**  
   長いリプレイからキルや集団戦を手動で探す必要がある。

2. **切り出し設定が煩雑**  
   前後何秒取るか、カメラ距離、視界（Fog of War）などを毎回調整するのが手間。

3. **外部リプレイが開きにくい**  
   現行の LoL リプレイ仕様では、ダウンロードしたリプレイを直接開けない場合がある。  
   ローカルリプレイ ID に合わせてファイル名をリネームし、ローカルリプレイフォルダへ上書きする運用が必要になる。

---

## 4. MVP（初期リリース）でやること

### 4.1 ハイライト自動検出

次の種類のシーンを検出する。

| 種別 | 説明（例） |
|------|------------|
| キル | 単発・連続キル、アシストを含むキル関連イベント |
| 集団戦 | 複数チャンピオンが短時間・近距離で交戦する区間 |
| オブジェクト周辺 | ドラゴン・バロン・タワーなどオブジェクト争奪に関わる場面 |
| その他 | 拡張可能な検出ルール（ソロキル、ペンタキル候補など） |

検出結果はタイムスタンプと種別・関連情報（参加者チャンピオン等）をメタデータとして保持する。

### 4.2 動画切り出し

- 検出時刻を基準に、**前後 N 秒**（例: ±10 秒）を動画として切り出す
- 切り出し前後の秒数は設定可能にする

### 4.3 録画・表示オプション（設定可能）

切り出し時の観戦／録画表示をユーザーが制御できるようにする。想定項目:

| 設定 | 内容 |
|------|------|
| カメラ距離 | 少し引く／近づける など |
| 視界（Fog of War） | オン／オフ、視点チャンピオン基準など |
| その他 UI 表示 | ミニマップ、スコアボード、ダメージ表示などの出し分け（実装可能な範囲で） |

※ 実際に制御できる項目は、リプレイクライアント／録画方式の制約に依存する。調査結果に応じて確定する。

### 4.4 リプレイファイル運用サポート

ダウンロードリプレイをローカルで開くための手順をツール側で支援する。

| 機能 | 説明 |
|------|------|
| ローカルリプレイ ID 指定 | 上書き先となる自分のローカルリプレイの ID を指定 |
| ファイル名リネーム | ダウンロードしたリプレイを、指定ローカル ID のファイル名に合わせてリネーム |
| ローカルフォルダへ配置／上書き | LoL のローカルリプレイフォルダへコピーまたは上書き |
| 元試合 ID の保持 | ファイル名変更で試合 ID が変わるため、**元のマッチ ID（および必要なら元ファイル名）をメタデータとして保持** |

保持しておく情報の例:

- 元マッチ ID / 元ファイル名
- 使用したローカルリプレイ ID（上書き先）
- 配置日時・パス
- （任意）検出ジョブや出力動画との紐付け

---

## 5. 想定ワークフロー（MVP）

```text
1. リプレイ取得
   └─ ダウンロード or ローカル既存ファイルを選択
2. （必要なら）ローカル再生用にリネーム＆配置
   └─ ローカル ID 指定 → リネーム → フォルダへ上書き
   └─ 元マッチ ID をメタデータに記録
3. リプレイ解析 / 再生連携
   └─ イベント・位置情報などからハイライト候補を検出
4. 候補レビュー（簡易 UI）
   └─ 採用／除外、前後秒数の微調整
5. 録画・切り出し
   └─ 設定（カメラ・視界など）を適用してクリップ保存
6. 出力
   └─ 動画ファイル + メタデータ（シーン種別、時刻、元マッチ ID 等）
```

## 7. 技術選定

### 7.1 結論

**コアは Python 3.12、UI は TypeScript（React）、最終配布は Tauri 2（Windows / WebView2）。**  
MVP は同じ Python バックエンドをローカル WebUI として起動し、ユーザーに Python / Node の手動インストールを要求しない形で配布する。

理由:

- ハイライト検出・ffmpeg・将来の AI 要約は Python エコシステムが最も強い
- LoL 連携の本丸は `.rofl` の完全デコードではなく、クライアント再生 + ローカル HTTP API（Replay API / Live Client Data @ `127.0.0.1:2999`）
- Windows 10/11 には WebView2 が入っていることが多く、Tauri なら追加ランタイムがほぼ不要
- Electron より軽く、将来の Discord 投稿・設定 UI・プレビューにも耐える

対象 OS は **Windows 専用**（LoL クライアント前提）。

### 7.2 採用スタック

| 層 | 技術 | 役割 |
|----|------|------|
| コアエンジン | Python 3.12 | リプレイ配置、検出、録画制御、切り出し、メタデータ |
| API | FastAPI | UI とエンジンの境界。ジョブ進捗・設定・候補一覧 |
| UI（MVP） | React + Vite（ローカルブラウザ） | 設定、候補レビュー、ジョブ実行 |
| UI（正式） | Tauri 2 + 同じ React | デスクトップアプリ化（ウィンドウ・トレイ・ファイルダイアログ） |
| 動画 | 同梱 ffmpeg | 切り出し・Shorts 用リフレーム等 |
| 永続化 | SQLite | 元マッチ ID、ローカル上書き先 ID、検出結果、出力パス |
| ROFL メタデータ | 既存パーサ活用（必要なら外部 CLI、または Python でヘッダのみ） | ファイル名・ゲームバージョン等。ペイロードは難読化のため深入りしない |
| 配布（MVP） | PyInstaller（one-folder）+ 同梱 ffmpeg | 解凍して exe 実行、ブラウザが開く |
| 配布（正式） | Tauri インストーラ + Python サイドカー | 通常の Windows アプリとしてインストール |

### 7.3 アーキテクチャ

```text
React UI ──► FastAPI ──► Python Engine ──► LoL Client
                              │               ▲
                              │               │ Replay / Live Client API
                              ├──► ffmpeg
                              └──► SQLite
```

主な処理フロー:

1. UI で `.rofl` とローカルリプレイ ID を指定
2. エンジンがリネーム／配置し、**元マッチ ID を SQLite に保存**
3. LoL でリプレイ起動 → Replay API でカメラ／視界／シーク制御
4. Live Client Data 等からキル・集団戦候補を検出（または再生中にイベント収集）
5. 前後 N 秒を録画／切り出し → ffmpeg で書き出し

### 7.4 採用しない案

- **Electron 単体**: 動くがバンドルが重く、Windows 専用にして利点が薄い
- **C# / WPF 単体**: Windows 配布は強いが、検出・ffmpeg・AI を伸ばすと Python 併設になりやすい
- **Python GUI のみ（Tk 等）**: MVP は速いが、将来のプレビュー／演出 UI で伸びにくい
- **ROFL ペイロード完全解析**: パッチごとに難読化され、メンテ不能になりやすい

### 7.5 パッケージ構成（コア）

| モジュール | 責務 |
|------------|------|
| `replay` | `.rofl` のリネーム・配置、ローカルフォルダ操作、元マッチ ID の扱い |
| `detect` | ハイライト候補の検出（キル・集団戦など） |
| `record` | LoL 再生制御・録画連携（Replay API 等） |
| `export` | ffmpeg による切り出し・変換 |
| `store` | SQLite へのメタデータ永続化 |

### 7.6 開発の進め方（技術面）

1. Python パッケージ構成を切る（上記モジュール）
2. FastAPI で「ファイル配置 + メタデータ保存」から実装
3. Replay / Live Client API の疎通検証（LoL 側設定含む）
4. 検出 MVP（キル中心）→ 切り出し
5. React WebUI を接続
6. 安定後に Tauri で同じ UI を包む

## 8. 技術的な検討事項（要調査）

実装前〜実装中に調査・検証する事項。

1. **リプレイから何を取れるか**  
   イベントログ、タイムライン API、クライアント再生制御、外部ツール連携の可否。

2. **録画方式**  
   クライアント内録画、画面キャプチャ、既製ツール連携など、どの方式が現実的か。

3. **リプレイファイル仕様**  
   拡張子・命名規則・ローカル保存パス・ID とマッチの対応関係。上書き運用のリスク（誤上書き防止）。

4. **検出ロジックの精度**  
   キルはイベントで取りやすい一方、集団戦・オブジェクト周辺はヒューリスティックやスコアリングが必要になる可能性。

5. **配布パッケージ**  
   PyInstaller → Tauri サイドカー移行時のパス解決、ffmpeg 同梱、WebView2 前提の確認。

## 9. 成功指標（案）

- 1 試合あたり、手動探しより短時間で使えるハイライトが得られる
- 主要なキル／集団戦を見逃しにくい（再現可能な検出基準）
- 外部リプレイのローカル再生準備が、手作業より少ない手順で完了する
- 切り出し前後秒数・表示設定が、再実行なしで調整できる（または設定を保存して使い回せる）

---

## 10. スコープ外（当面やらないこと）

- 公式配信のリアルタイム切り出し（VOD／ライブ専用パイプライン）
- 他タイトル対応
- 商用配信プラットフォームへの完全自動アップロード一式（将来構想の一部として別途設計）

## 11. ドキュメント更新方針

本企画は初期草案である。検出ルール・録画方式・リプレイ運用の調査結果に応じて、MVP の境界と設定項目を更新する。技術選定（第7節）は実装の前提として扱い、大きな変更時のみ更新する。
